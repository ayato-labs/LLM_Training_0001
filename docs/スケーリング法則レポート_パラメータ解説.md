## 1. レポートの全体構造と計算パイプライン

レポートは**単一の自己整合的な計算チェーン**から生成される。中心となる原則は以下である。

1. **計算予算はトークンではなく FLOPs で定義する**（専門家コンセンサス。トークン/sec はモデル規模に依存するため、プロキシ実測値をそのまま流用すると誤差が生じる）
2. **Chinchilla の黄金比 $D = 20N$** と **$C = 6ND$** から、予算 $C$ に対して $N = \sqrt{C/120}$ を導出
3. **VRAM 実測値は実行可能上限としてモデル規模を制約**し、データ不足は警告のみ（データは追加収集可能なため）

### 計算フロー

```
実測スループット (プロキシモデル)
        │  × プロキシ規模 × 1トークンあたりFLOPs (8N or 6N)
        ▼
実効FLOPsレート [FLOPs/s] ──× ターゲット時間 ──► 総計算量 C [FLOPs]
        │
        ▼
純粋 Compute-Optimal N = √(C/120), D = 20N
        │  × VRAM実測値 (bs=1で収まる最大Nを二分探索)
        ▼
推奨モデル規模 N (量子化済みアーキテクチャ)
        │
        ├─► 計画D = C / (8N)          … 1000hで処理できるトークン数
        ├─► 予測スループット = 実効FLOPs / (8N)
        ├─► 予測学習時間 = 計画D / 予測スループット = ターゲット時間 (自己整合)
        ├─► 20N最適予算 = 20 × N       … そのモデル自身の理論最適トークン量
        └─► データ充足率 = 実データ / 計画D
```

以降、各セクションのパラメータを 1 つずつ解説する。

## 2. ヘッダー部

### 2.1 GPU Hardware（GPUハードウェア）

```
GPU Hardware : NVIDIA GeForce RTX 3050 Laptop GPU (Total VRAM: 4.0 GB)
```

| 項目 | 意味 |
|------|------|
| デバイス名 | `torch.cuda.get_device_properties(0).name` から取得した GPU の物理名称 |
| Total VRAM | GPU の**物理搭載** VRAM 総量（4.0 GB）。空き容量ではない |

**読み取り方**: 物理的な上限。実際に使える量は後述の「Real Free VRAM」で測る。CUDA 非利用時は 4.0 GB のフォールバック値になる。

### 2.2 Measured Throughput（実測スループット）

```
Measured Throughput  : 57809.7 tokens/sec (Source: proxy_benchmark)
```

| 項目 | 意味 |
|------|------|
| 値 | GPU が**1秒間に処理できるトークン数**の実測値 |
| Source | 値の入手経路。`proxy_benchmark`（プロキシモデルの実測）/ `recent_logs`（学習ログからの抽出）/ `user_input`（手入力） |

**計算方法**: 27M 規模のプロキシ LLaMA モデルを GPU 上で実際に forward/backward し、`tokens/sec = (バッチ×シーケンス長) / 1ステップ秒数` で計測。

**読み取り方**: **この値はプロキシモデル（27M）の速度であり、推奨モデルの速度ではない**。推奨モデルの速度は FLOPs 補正された「Projected Throughput」を参照する。

### 2.3 Total Tokens (D)（総トークン数・学習計画D）

```
Total Tokens (D)     : 22,362,765,272 tokens (22362.77M) - plan for the recommended model in 1000.0h
```

| 項目 | 意味 |
|------|------|
| 値 | **推奨モデルをターゲット時間（1000h）学習したときに処理されるトークン数**の見積もり |

**計算式**:

$$D = \frac{C}{8N} = \frac{(\text{実効FLOPs/s} \times \text{ターゲット時間})}{8 \times N_{\text{推奨}}}$$

（Gradient Checkpointing 有効時は 1トークンあたり 8N FLOPs、無効時は 6N）

サンプルでは $D = 22{,}362{,}765{,}272$ tokens ≈ 223.6 億トークン。データセット実測が 13.9 億トークンなので、**データが計画 D の 6.2% しかない**ことが後段の Dataset Audit で警告される。

**読み取り方**: モデル規模と時間予算が変われば D も変わる「計画値」。キャップがかからない場合（推奨モデル＝純粋最適）は $D = 20N$ と一致する。

### 2.4 Context Length（コンテキスト長）

```
Context Length : 512 tokens
```

`base_config.yaml` の `training.seq_len` から取得される**1サンプルあたりのトークン数**（シーケンス長）。活性化メモリ量・FLOPs・バッチサイズのすべてに影響する。

## 3. Recommended Model Architecture（推奨モデルアーキテクチャ）

### 3.1 Pure Compute-Optimal N (reference)（純粋 Chinchilla 最適規模・参考値）

```
Pure Compute-Optimal N (reference) : 617.29M
```

**計算式**（Chinchilla: $C = 6ND$ かつ $D = 20N$ より）:

$$N_{\text{pure}} = \sqrt{\frac{C}{120}}$$

サンプル: $C = 1.2703 \times 10^{13} \times 3{,}600{,}000 = 4.5731 \times 10^{19}$ FLOPs → $N_{\text{pure}} = 617.29$M

| 項目 | 意味 |
|------|------|
| 値 | 時間予算 C を全て使い切る場合の理論最適モデル規模（Hoffmann et al., 2022） |
| 位置づけ | あくまで**参考値**。VRAM や量子化の制約を考慮しない純粋な理論値 |

### 3.2 Model Parameters (N)（モデルパラメータ数・最終推奨値）

```
Model Parameters (N) : 255,590,400 (~255.59M)
```

**決定ロジック**:

$$N_{\text{推奨}} = \min(N_{\text{pure}},\; N_{\text{VRAM上限}})$$

- $N_{\text{VRAM上限}}$: micro_batch=1 の推定ピークVRAMが「空きVRAM × 0.90」に収まる最大の規模を**二分探索**で算出
- データ不足では縮小しない（警告のみ）

サンプルでは、純粋値 617.29M に対し**量子化後の実アーキテクチャが 255.59M** になった。`generate_universal_architecture` が hidden size を 128 の倍数・層数を整数に丸めるため、中間規模ではターゲット N より小さなアーキテクチャになることがある。

### 3.3 Hidden Size / Num Layers / Attention Heads / KV Heads / Intermediate Size

```
Hidden Size          : 1280
Num Layers           : 10
Attention Heads      : 20 (KV Heads: 5)
Intermediate Size    : 3456
```

`generate_universal_architecture(target_n)` が幾何スケーリングで自動設計する LLaMA アーキテクチャ。

| 項目 | 意味 | 導出 |
|------|------|------|
| Hidden Size $H$ | 隠れ層次元 | $H = \lfloor 512 \times (N/37\text{M})^{1/3} / 128 \rceil \times 128$ |
| Num Layers $L$ | トランスフォーマー層数 | $L = \lfloor 4 \times (N/37\text{M})^{1/3} \rceil$（最低2層） |
| Attention Heads | 注意ヘッド数 | $H / 64$（最低4） |
| KV Heads | GQA の KV ヘッド数 | ヘッド数 / 4（最低1） |
| Intermediate Size $I$ | SwiGLU FFN 中間次元 | $I = \lfloor 2.67 \times H / 128 \rceil \times 128$ |

**検証**: PyTorch meta device 上で `LlamaForCausalLM` を実際に構築し、パラメータ数を実測して `n_params` に反映する（近似式ではなく実数）。

### 3.4 Projected Throughput（推奨モデルの予測スループット）

```
Projected Throughput : 6,211.9 tokens/sec (recommended model)
```

**計算式**:

$$\text{projected\_tps} = \frac{\text{実効FLOPs/s}}{8 \times N_{\text{推奨}}} = \text{実測tps} \times \frac{N_{\text{プロキシ}}}{N_{\text{推奨}}}$$

サンプル: $57{,}809.7 \times \frac{27.46\text{M}}{255.59\text{M}} = 6{,}211.9$ tps

**読み取り方**: プロキシ実測値（57,809 tps）は 27M モデルの速度なのでそのまま使えない。FLOPs 換算すると推奨モデル（255.59M）は約 **1/9.3 の速度**になる。この数値こそが実運用時の実効速度の見積もり。

### 3.5 Predicted Training（予測学習時間）

```
Predicted Training   : ~1,000.0 hours (41.7 days) to process 22362.77M tokens
```

**計算式**:

$$\text{予測時間} = \frac{\text{計画}D}{\text{projected\_tps}} = \frac{C / (8N)}{(\text{実効FLOPs/s}) / (8N)} = \frac{C}{\text{実効FLOPs/s}} = \text{ターゲット時間}$$

**自己整合性の保証**: 計画 D と予測スループットは同一の FLOPs レートから導出されるため、予測学習時間は**必ずターゲット時間と一致する**。旧実装では「プロキシ tps × 時間」で D を決めていたため、推奨モデルの実時間が 9,300h と 10 倍近く乖離するバグがあった。FLOPs ベース導出により構造的に解決されている。

### 3.6 Chinchilla Budget (20N)（モデル自身の理論最適データ量）

```
Chinchilla Budget    : 5,111,808,000 tokens (20N) = ~228.6 hours at projected throughput
```

**計算式**: $20 \times N_{\text{推奨}} = 20 \times 255{,}590{,}400 = 5{,}111{,}808{,}000$ tokens

**意味**: 推奨モデルが Chinchilla 黄金比（データ:パラメータ = 20:1）を満たすために必要なトークン量。これを予測スループットで割ると所要時間 **228.6h**。

**読み取り方**: 3.2 と比較すると「**推奨モデルは 1000h のうち約 229h で理論最適データ量に到達し、残りの 771h はデータが不足する（オーバートレーニング領域）**」ことが分かる。これが Dataset Audit の警告（充足率 6.2%）につながる。

## 4. VRAM & Physical Micro-Batch Split Safety（VRAM 安全検証）

### 4.1 Real Free VRAM（実測空きVRAM）

```
Real Free VRAM : 3.16 GB
```

`torch.cuda.mem_get_info()` で CUDA コンテキストを初期化した直後の**実際に利用可能な空き容量**。物理搭載 4.0 GB との差（0.84 GB）は Windows デスクトップ・他のプロセス・GPU ドライバの固定使用分。

### 4.2 Estimated Peak VRAM（推定ピークVRAM）

```
Estimated Peak VRAM : 2.7722 GB / 4.0 GB
```

**内訳**（`src/common/vram_estimator.py`）:

| 成分 | 計算 | サンプル寄与 |
|------|------|--------------|
| モデル重み | $N \times 2$ bytes (bf16) | 0.48 GB |
| 勾配 | $N \times 2$ bytes | 0.48 GB |
| オプティマイザ状態 | $N \times 2$ bytes (AdamW 8bit) | 0.48 GB |
| 活性化 | チェックポイントモード依存（full なら微小） | ≈ 0 |
| Liger FLCE ワークスペース | logitsチャンク + grad_weight | 0.18 GB |
| CUDA コンテキスト | 実測キャリブレーション値 | 0.05 GB |
| アロケータ断片化 | 合計 × キャリブレーション係数 1.4762 で増幅 | 1.10 GB |

**読み取り方**: 「空きVRAM 3.16 GB × 0.90（安全率）= 2.84 GB」が実質的な実行上限であり、2.7722 GB はそれを下回る（マージン約 2.4%）。`vram_calibration.json` の実測値（allocator_factor 1.4762 等）が存在すれば実測優先で計算される。

### 4.3 Safety（安全性フラグ）

```
Safety : OK
```

- **OK**: 推定ピーク ≤ 物理VRAM
- **DANGER**: 超過。モデルを縮小するか、`torch_compile` を無効化するか、バッチを減らす必要がある

推奨アーキテクチャは VRAM 上限を満たすように決定されるため、原則 OK になる。

### 4.4 Physical Micro-Batch（物理マイクロバッチ分割）

```
Physical Micro-Batch : per_device_batch_size=88, grad_accum_steps=1 -> Total Batch=88
```

| 項目 | 意味 | サンプル |
|------|------|---------|
| per_device_batch_size $b_{\text{micro}}$ | 1回の forward/backward で GPU に載せるサンプル数 | 88 |
| grad_accum_steps $G_A$ | 勾配蓄積ステップ数 | 1 |
| Total Batch $B_{\text{total}}$ | 理論最適トータルバッチ = $b_{\text{micro}} \times G_A$ | 88 |

**計算方法**（2段階分離型バッチ設計）:

1. **Critical Batch Size 則**（McCandlish/Kaplan）: $B_{\text{total}} = 64 \times (N / 86.5\text{M})^{0.3}$ で理論最適トータルバッチを算定
2. **VRAM 制約**: 「推定ピーク ≤ 空きVRAM × 0.90」を満たす**最大の** $b_{\text{micro}}$ を 2 の冪乗候補から選択
3. $G_A = \lceil B_{\text{total}} / b_{\text{micro}} \rceil$ で結合

サンプルでは 88 サンプル × 512 token = 45,056 token/ステップ が 1 バッチ。**VRAM に収まるなら $G_A = 1$ が最速**（勾配蓄積ループの Python/Autograd オーバーヘッド最小化）。

> **注意**: $b_{\text{micro}} = 1$ でも VRAM 上限を超えるアーキテクチャは「VRAM infeasibility」エラー（ValueError）で明確に拒否される。黙って無意味な分割を返さない。

## 5. Dataset Audit（データセット監査）

### 5.1 Data Path / Actual Tokens / Sufficiency Ratio

```
Data Path            : data/dataset.jsonl
Actual Tokens        : ~1388.06M tokens
Sufficiency Ratio    : 6.2%
```

| 項目 | 意味 |
|------|------|
| Data Path | 事前学習データセットの実パス |
| Actual Tokens | データセットの実測トークン数（JSONL をサンプリング計測、token/char 比から推定） |
| Sufficiency Ratio | $\frac{\text{実データトークン}}{\text{計画}D} \times 100$ |

サンプル: $1{,}388.06\text{M} / 22{,}362.77\text{M} = 6.2\%$。**計画 D の 6.2% しかデータがない**。

### 5.2 WARN: データ不足

```
[WARN] Dataset tokens are insufficient for pure compute-optimal training!
       Dataset Tokens : ~1388.06M tokens (required: 22362.77M, sufficiency: 6.2%)
       Data-Capped Model Size (reference): 46,284,800 (~46.28M) - collect more data...
```

| 項目 | 意味 |
|------|------|
| required | 計画 D（推奨モデルが 1000h で処理するトークン量） |
| Data-Capped Model Size (reference) | **もしデータ量を固定するなら**許容される規模 $\text{実データ}/20 = 69.4\text{M}$ → 量子化アーキ 46.28M。あくまで参考値 |

**設計意図**: データ不足は**警告のみ**でモデル規模を縮小しない。データは後から収集すれば良いため、推奨モデルは VRAM 実行可能上限を基準に決定される。「46.28M にすべき」ではなく「**22,363M トークン分のデータを集めるべき**」と読む。

### 5.3 WARN: VRAM 不足（キャップ適用時のみ表示）

```
[WARN] Pure Compute-Optimal (D = 20N) is NOT feasible on the current VRAM!
       Pure Optimal requires ~32.34 GB -> VRAM-Capped Model Size: 255,590,400 (~255.59M) is applied
```

純粋な Compute-Optimal の推定ピーク VRAM が空き VRAM の安全上限（×0.90）を超える場合にのみ表示される。推奨モデル = VRAM キャップ適用済み値であることを明示する。サンプル（1000h）では純粋最適 617.29M が量子化後に 255.59M となり収まるため、この警告は出ない。

## 6. HPO Simulation（ハイパーパラメータ探索シミュレーション）

### 6.1 Proxy Model Size（プロキシモデル規模）

```
Proxy Model Size : 30,277,632 (~30.28M)
```

HPO（Optuna）で実際に学習・評価するプロキシモデルの規模。

**計算式**: $\min(N_{\text{推奨}},\; \max(50\text{M},\; 0.1 \times N_{\text{推奨}}))$

サンプル: $\min(255.59\text{M},\; \max(50\text{M},\; 25.56\text{M})) = 50\text{M}$ → 量子化アーキ 30.28M。ターゲットの約 10%（下限 50M）で探索することで、探索時間と転移精度のバランスを取る。

### 6.2 Estimated Search Time（予測探索時間）

```
Estimated Search Time: ~17.5 mins (MedianPruner) / ~50.0 mins (Worst-Case)
```

| 項目 | 意味 |
|------|------|
| Worst-Case | 枝刈りなしの場合の全試行時間 = トライアル数 × 50 ステップ × 0.5秒/ステップ |
| MedianPruner | Optuna 中央値枝刈りで早期に不良試行を打ち切る場合の期待時間（worst-case の約 35%） |

## 8. 付録: 用語集

| 用語 | 説明 |
|------|------|
| Chinchilla 則 | DeepMind (Hoffmann et al., 2022)。計算量 C、パラメータ数 N、データ量 D の最適比率 $D = 20N$、$C = 6ND$ |
| FLOPs | Floating Point Operations。モデル規模×トークン数の計算量の単位 |
| MFU | Model FLOPs Utilization。理論ピーク演算能力に対する実効利用率 |
| Gradient Checkpointing | 活性化を保持せず backward で再計算する手法。FLOPs は 6N→8N/token に増加するがメモリは激減 |
