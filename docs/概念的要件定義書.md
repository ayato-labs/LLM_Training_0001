# 概念的要件定義書

- **作成日**: 2026-07-30
- **最終更新日**: 2026-07-30

本書は、LLM フルスクラッチ事前学習フレームワーク `LLM_Training` における **実装方針の論理的根拠** を記述する。
機能目標や計画ではなく、「何を・何で・どの方針で実装するのか」および「何を・何で・どの方針で実装しないのか」を明文化し、将来の設計判断の一貫性を担保する。

---

## 1. システム境界と対象範囲

### 1.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| 単一 GPU 環境での LLM フルスクラッチ事前学習 | VRAM 4GB ~ 48GB の単一 GPU を前提とし、全パイプラインを単一プロセスで完結させる | ハイパースケーラー以外の個人・研究環境において、分散学習のインフラ構築コストなしに LLM 事前学習を実行可能にするため |
| 4 段階パイプライン（Scaling Laws → HPO → Pretraining → Context Extension） | 各段階を独立サブシステムとして分離し、一方通行 DAG で接続する | 段階間の循環依存を排除し、任意の段階を単独で再実行可能にするため |
| LLaMA アーキテクチャ (Decoder-only Transformer) | HuggingFace `LlamaForCausalLM` を唯一のモデルアーキテクチャとして採用する | アーキテクチャの汎用性を追求するよりも、単一アーキテクチャの最適化深度を優先するため |

### 1.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| マルチ GPU 分散学習 (DDP / FSDP / DeepSpeed ZeRO) | 単一 GPU 完結を前提とし、分散学習の抽象化レイヤーを持たない | 分散学習は通信オーバーヘッド・同期プロトコル・ランチャースクリプトなど、単一 GPU とは本質的に異なるコードパスを要求する。中途半端な抽象化はどちらの環境でも最適性を損なう |
| Encoder-only / Encoder-Decoder アーキテクチャ | LLaMA (Decoder-only) 以外のアーキテクチャには対応しない | モデルアーキテクチャの多様性を吸収する汎用レイヤーは、各アーキテクチャ固有の最適化（RoPE, GQA, SwiGLU 等）を犠牲にする |
| SFT / RLHF / DPO 等のアライメントフェーズ | 事前学習とコンテキスト拡張までをスコープとし、ファインチューニングは外部ツールに委ねる | SFT/RLHF は報酬モデル・対話データセット・評価基盤など、事前学習とは独立した複雑性を持つ |
| 推論最適化 (量子化 / KV Cache / Speculative Decoding) | 学習パイプラインの範囲外とする | 推論時の最適化は学習時の制約（勾配計算、オプティマイザステート保持）と根本的に異なる |

## 2. スケーリング法則エンジン (`src/scaling_laws/`)

### 2.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| Chinchilla 則 (Hoffmann et al., 2022) による最適モデル規模の逆算 | 目標学習時間 → 計算可能トークン数 $D$ → $N_{\text{opt}} = D / 20$ の一方向計算で、モデルアーキテクチャを自律決定する。`base_config.yaml` の `gradient_checkpointing` 設定（有効時 8N FLOPs/token, 無効時 6N FLOPs/token）をプロキシベンチマークと演算量補正の両方に反映する | 人手による「とりあえず 150M」のような恣意的なモデル規模選択を排除し、全層 Gradient Checkpointing の再計算オーバーヘッド（約 33% 増加）を含めた真の計算予算に対して理論最適な規模を自動導出するため |
| 限界バッチサイズ法則 (McCandlish/Kaplan, 2018-2020) による理論最適バッチサイズの算定 | $B_{\text{crit}} \propto N^{0.3}$ のべき乗則でトータルバッチサイズを算定する | バッチサイズは「HPO で探索すべきハイパーパラメータ」ではなく「GPU 物理 VRAM と収束理論から決定されるハードウェアパラメータ」であるという設計原則に基づく |
| 2 段階分離型マイクロバッチ設計 (Decoupled Batch Architecture) | 理論最適トータルバッチ $B_{\text{total}}$ と VRAM 90% 安全上限を照合し、物理的に収まる最大マイクロバッチ $b_{\text{micro}}$ を直接割り当てる | Tensor Core の演算器充填率（MFU）を最大化し、勾配蓄積のループ回数（=Python/Autograd オーバーヘッド）を物理的最小にするため |
| GPU 実測 VRAM キャリブレーション (`auto_calibrate`) | モデルを GPU 上に構築し forward/backward の VRAM 増分を実測、`vram_calibration.json` に保存する | 計算式のみの推定では CUDA Caching Allocator の断片化率、Liger FLCE chunked backward のワークスペース等を正確に見積もれないため |
| LLaMA 幾何学的アーキテクチャの動的自動生成 (`generate_universal_architecture`) | ターゲットパラメータ数 $N$ から (hidden_size, num_layers) の**グリッド探索**（128 倍数・整数層数の全候補を解析式で評価）で相対誤差が **±15% 以内**（可能な限り最小、同点時は下振れより上振れ優先）になるアーキテクチャを選択し、選択後に meta device 実測でパラメータ数を確定する | 固定プリセット (`if 150M` / `elif 3B`) の分岐を排除し、任意のパラメータ数に対して連続的にスケールするため。単純な丸め（単一スケール式）では中間規模で **-47% 級の大幅下振れ**（87.15M → 46.28M 等）が発生し、実 VRAM・実学習時間と乖離するため |
| Tensor Core 飽和スループット実測 (`run_quick_proxy_benchmark`) | VRAM 物理算定式で求めた物理最速バッチサイズと `LlamaModel` バックボーンで、`base_config.yaml` の Gradient Checkpointing やオプティマイザ設定を動的反映した状態で Tensor Core 飽和スループットを実測する | `batch_size = 1` や Checkpointing なしでの測定では再計算オーバーヘッドが無視され、本番学習時間との計算剥離が発生するため |

### 2.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| バッチサイズの HPO 探索 | バッチサイズを Optuna の探索空間に含めない | バッチサイズは VRAM 物理容量と収束理論（限界バッチサイズ）から一意に決まるため、確率的探索の対象にすべきでない |
| 複数 GPU 構成を考慮した `per_device_batch_size` の自動分割 | 単一 GPU の VRAM 容量のみを基準とする | マルチ GPU 環境ではデバイス間の勾配同期タイミングが分割戦略に影響するため、単一 GPU の論理と同一視できない |

## 3. HPO サブシステム (`src/hpo/`)

### 3.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| Step Law (arXiv:2503.04715) による探索空間の事前絞り込み | $\eta^*(N, D) = 1.79 \cdot N^{-0.713} \cdot D^{0.307}$ から中心点を算出し、$[0.5\times, 2.0\times]$ の対数空間で探索する | 広域グリッドサーチや無計画なベイズ最適化は計算予算に対して非効率であり、理論予測値を事前分布として活用することで探索範囲を最適化する |
| プロキシモデルによる低コスト探索 → ターゲット規模への転移 | $N_{\text{proxy}} = \min(N_{\text{target}}, \max(50\text{M}, \lfloor N_{\text{target}} \times 0.10 \rfloor))$ で動的にプロキシ規模を算定する（ターゲットが 50M 未満の場合はターゲットサイズをそのまま使用） | 本番規模モデルでの HPO は 1 試行あたりの計算コストが高すぎるため、小規模プロキシでの探索結果を Step Law の理論比率で外挿する。プロキシがターゲットより大きくなると外挿比が逆転するため、ターゲット未満に上限を制約する |
| 探索空間次元数に基づく試行回数の自動算定 | $T_{\text{trials}} = D \times 30$ （$D$: 探索空間の自由度、現状 4 次元）で算定する | 特定モデルサイズへの手動過剰適合式を排除し、次元数の変化に対してスケールする算定式にするため |
| VRAM Estimator による Zero-Cost Pre-Pruning | 試行評価直前に推定 Peak VRAM が物理容量の 90% を超える設定を検知し、GPU プロセスを起動せず `TrialPruned` を発動する | OOM クラッシュによる GPU ドライバリセット → 10 秒のリカバリ待機 → 残り全試行の時間浪費を防止するため |
| `spawn` コンテキストによる子プロセス隔離 | 各 HPO 試行を `multiprocessing.get_context("spawn")` の子プロセスで実行する | CUDA OOM や TDR による GPU ドライバリセットが親プロセス（Optuna ループ）を巻き込まないようにするため |
| 親プロセスの CUDA Context 初期化回避 | 親プロセスでは `torch.cuda.*` を直接呼ばず、VRAM 検出は `nvidia-smi` CLI 経由で行う | 親プロセスで CUDA Context を初期化すると約 0.3~0.7 GB の VRAM が常駐し、子プロセスの学習可能 VRAM が減少するため |
| Optuna MedianPruner による枝刈り | 損失値の中間値に基づいて劣位試行を早期打ち切りする | 探索効率を維持しつつ、明らかに収束の見込みがない設定の計算コストを削減するため |

### 3.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| HPO と本番学習の依存関係 | 本番学習コード (`src/training/main.py`) は `optuna` を import しない | HPO は開発時のみ実行されるオフライン処理であり、本番学習に HPO ライブラリの依存を持ち込むと依存関係が肥大化する |
| アーキテクチャ探索 (NAS) | レイヤー数 / hidden_size 等のアーキテクチャパラメータは HPO の探索対象にしない | アーキテクチャは Chinchilla 則で理論的に決定済みであり、HPO はその固定アーキテクチャ上のハイパーパラメータ（学習率、weight decay 等）のみを最適化する |

## 4. 学習エンジン (`src/training/`)

### 4.1 オプティマイザ戦略

#### 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| Muon (2D) + AdamW 8bit (1D) の分離最適化 (`SplitOptimizer`) | 2D 重み行列は Newton-Schulz 直交化ベースの Muon で、1D パラメータ（Embedding, Bias, LayerNorm）は `bitsandbytes` の AdamW 8bit で最適化する | Muon は 2D 重み行列の直交構造を活用して高速収束するが、1D パラメータには直交化の意味がない。AdamW 8bit はオプティマイザステートの VRAM 消費を 8bit 量子化で約 0.3~0.5 GB 削減する |
| 1D / 2D パラメータの Weight Decay 分離 | 2D 重み行列のみ `weight_decay = 0.1` を適用し、1D パラメータは `weight_decay = 0.0` にする | LayerNorm のスケール係数や Bias に L2 正則化を適用すると表現力が理不尽に減衰するため |
| Newton-Schulz 反復数のモデル規模連動動的判定 | $d_{\text{model}} < 2048$ → `steps = 3`、$d_{\text{model}} \ge 2048$ or $N \ge 1\text{B}$ → `steps = 5` | 小規模モデルでは 3 反復で十分な直交化精度が得られるが、大規模モデルでは行列の条件数により精度不足となるリスクがあるため |
| Newton-Schulz 演算の JIT コンパイル (`@torch.jit.script`) | `zeropower_via_newtonschulz` 関数を C++ レベルで最適化する | 毎ステップ実行される直交化ループの Python 側呼び出しオーバーヘッドを排除するため |
| 学習率の安全上限と二重ガード (SSOT + Defense in Depth) | `constants.py` に `MAX_LR_2D = 0.02`, `MAX_LR_1D = 0.0010` を SSOT として定義し、HPO 探索空間算定時と Config 正規化時の双方から参照する | Muon は更新量が大きく、無制限な高学習率では Loss 発散リスクがあるため。二重ガードにより設定不整合時の安全性を構造的に担保する |

#### 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| Embedding 層 / LM Head への Muon 適用 | `embed_tokens` / `lm_head` は Muon の対象外とし AdamW で処理する | Embedding 行列は語彙 × 隠れ層の疎なルックアップテーブルであり、直交化ベースの更新は意味的に不適切 |
| FP32 AdamW のフォールバック以外のオプティマイザ | Muon + AdamW 8bit 以外の選択肢（LAMB, Lion 等）を能動的にサポートしない | オプティマイザの多様性を追求するよりも、Muon の直交化と AdamW 8bit の VRAM 効率の組み合わせに特化するため |

### 4.2 VRAM 管理戦略

#### 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| 全層フル Gradient Checkpointing (`use_reentrant=False`) | HuggingFace 標準の全層 Gradient Checkpointing に一本化する | Liger Kernel (Triton) との選択的チェックポイントの組み合わせは、テンソル形状不一致による Autograd デッドロックを引き起こすことが検証で確認されたため |
| Liger Kernel (Triton Fused Kernel) の採用 | SwiGLU / RMSNorm / CrossEntropy を Triton カーネルで融合し、Linux 環境で有効化する | 個別の PyTorch 演算子を GPU カーネル呼び出し単位で融合することで、カーネル起動オーバーヘッドと中間テンソルの VRAM 消費を同時に削減するため |
| Liger Kernel Triton JIT 事前ウォームアップ | 本番学習ループ開始前に、対象モデルの実寸法テンソルで各 Triton カーネルを個別にコンパイル・同期する | 初回 Forward Pass での 10~30 秒の GPU ストールが WSL2 環境で Windows TDR タイムアウトを引き起こすのを防止するため |
| 統一 VRAM 推定エンジン (`vram_estimator.py`) | 重み・勾配・オプティマイザステート・活性値・Liger FLCE ワークスペース・CUDA Context・Allocator 断片化を一元推定する | VRAM 見積もりの重複実装を排除し、全 caller が同一の推定ロジックを参照することで精度を一元管理するため |
| CUDA Caching Allocator のフラグメンテーション制御 | `PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.8,max_split_size_mb:128` を環境変数で設定する | Reserved メモリの不要な拡大と断片化による OOM を防止するため |

#### 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| 選択的 Gradient Checkpointing（Attention のみ再計算） | Liger Kernel 使用時は無効化する | Liger の動的アラインメント（例: `5120` → `5632`）が Attention/MLP 境界で PyTorch Autograd の再計算フック (Unpack Hook) とテンソル形状不一致を起こし、`CheckpointError` → C++ デッドロックに至ることが検証済み |
| `torch.compile` (Inductor) の Liger Kernel 併用 | 同時使用時は警告を出力し、推奨しない | Triton カスタム autograd 関数と TorchDynamo のトレーシングが Graph Break を多発させ、Eager フォールバックでメリットが消失するため |
| CPU Offloading (ZeRO-Offload 等) | 単一 GPU の VRAM 内で完結させる | CPU-GPU 間のデータ転送レイテンシが学習速度を著しく低下させるため |

### 4.3 計算効率戦略

#### 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| Sequence Packing（パディングトークン排除） | 全テキストを EOS トークン区切りで結合し、固定長 `seq_len` でスライスする | パディングトークンへの無駄な計算（Forward/Backward 両方）を 100% 排除するため |
| cuDNN Benchmark モード (`cudnn.benchmark = True`) | Sequence Packing により入力長が完全定長であることを前提に有効化する | 第 1 ステップでカーネル試行テストを行い、GPU に最適な cuDNN カーネルを自動選択・固定するため。可変長入力では逆効果 |
| Tensor Core float32 行列積精度 `medium` モード | `torch.set_float32_matmul_precision("medium")` を適用する | Ampere 世代以降の GPU で FP32 行列積を TF32 精度（仮数部切り捨て）で計算し、実用上の精度低下を極めて軽微に抑えつつ全 Linear 層を 10~20% 高速化するため |
| SDPA 低速 Pure Math フォールバックの禁止 | `torch.backends.cuda.enable_math_sdp(False)` を明示的に呼び出す | FlashAttention / Efficient Attention カーネルのみを強制選定し、低速な Python/C++ 実装への自動退避を防止するため |
| FlashAttention バックエンドのディスパッチ検証 | 学習開始前に SDPA 経由で FlashAttention カーネルが正常に選択されることを明示的にテストする | サイレントフォールバック（ログなしに低速カーネルに切り替わる挙動）を検知するため |
| 重み共有 (Weight Tying) | Embedding 層と LM Head の重み行列を転置結合する | パラメータ数の削減（約 2,450 万パラメータ軽量化）と行列乗算の高速化を同時に達成するため |
| 保存・評価頻度の分離 | チェックポイント保存（高頻度 `save_steps`）と生成評価（低頻度 `eval_steps`）を独立制御する | テキスト生成評価は Auto-regressive 推論で GPU を一時停止させる高コスト処理であり、保存と同頻度で実行すると不要な空転が発生するため |
| TF32 (TensorFloat-32) の有効化 | `torch.backends.cuda.matmul.allow_tf32 = True` を設定する | Ampere 世代以降の GPU で行列演算を高速化するため |
| DataLoader の動的パフォーマンス適合 | OS / CPU コア数 / ストレージ種別に応じて `num_workers` を自動判定する | Windows WDDM デッドロック防止上限と Linux CPU コア数上限のハイブリッド判別により、マルチプロセス通信のクラッシュ回避と GPU 空転率最小化を両立するため |

#### 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| 可変長シーケンスのバッチ処理 | Sequence Packing により全入力を固定長 `seq_len` に統一するため、動的パディングや Bucket Batching を実装しない | 固定長入力は cuDNN Benchmark モードの前提条件であり、可変長対応は cuDNN の再プロファイリングを毎ステップ誘発して速度低下を招く |
| Mixture of Experts (MoE) | 密結合 (Dense) モデルのみを対象とする | MoE はルーティングロジック・負荷分散・Expert 並列化など、密結合モデルとは根本的に異なる計算パターンを要求する |

### 4.4 安定性・トレーサビリティ戦略

#### 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| 多重自律発散検知（語彙数動的理論上限 + 相対スパイク判定 + NaN/Inf 監視） | 3 重の独立した監視ロジックで学習の異常を検知する | 単一の固定閾値では語彙数変更による初期 Loss 理論値の変化で誤判定が発生し、学習途中の局所発散を見逃すため |
| ハッシュ自動検証付き学習再開 (`hashes.json`) | チェックポイント保存時に Config と学習データの SHA256 ハッシュを記録し、再開時に自動検証する | 異なる設定パラメータや異なるデータセット状態での誤った再開によるモデル重み汚染を 100% 防止するため |
| 絶対値での Warmup ステップ確保 (`warmup_steps: 50`) | 比率指定 (`warmup_ratio`) のみではなく、最低 50 ステップの絶対値保証を設ける | ステップ数が少ない実験時にウォームアップが 1~2 ステップで終了し、初期のランダム重みに急激な勾配更新が印加されるのを防止するため |
| Hydra + OmegaConf による設定管理 | 全設定を YAML ファイルで宣言的に管理し、CLI オーバーライドと defaults 合成をサポートする | 実験の再現性と設定変更の追跡可能性を確保するため |
| DVC によるデータ版管理 | 学習データを SHA256 ハッシュで版管理する | データの変更を Git と同等のトレーサビリティで追跡するため |
| TensorBoard による実験追跡 | 損失値・学習率・勾配ノルム等をステップ単位で記録する | 学習の進行状況と異常の可視化を低オーバーヘッドで実現するため |
| 乱数シード固定 (`set_seed()`) | PyTorch / NumPy / Python random / CUDA のシードを一括固定する | 実験の再現性を担保するため |

#### 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| W&B / MLflow 等の外部実験管理プラットフォーム | TensorBoard のみを採用する | 外部サービスへの依存と認証管理を排除し、ローカル完結の軽量な実験追跡にするため (ADR-0016) |
| 独自の学習ループ実装 | HuggingFace `Trainer` を基盤として使用し、カスタマイズはコールバックとサブクラスで行う | gradient accumulation / mixed precision / checkpointing の再実装は正確性・保守性の両面でリスクが高いため |

## 5. コンテキスト拡張サブシステム (`src/context_extension/`)

### 5.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| 事後長文拡張 (Continued Pretraining) としての独立モジュール分離 | `src/context_extension/` を事前学習コードから完全に分離し、独自のエントリーポイントを持つ | 事前学習コード (`train_engine.py`) にコンテキスト拡張ロジックを埋め込むと、条件分岐の増加によるコード煩雑化と二重管理が発生するため |
| RoPE Scaling (YaRN / Dynamic NTK) の動的注入 | 学習済みモデルの `config.rope_scaling` を事後的に書き換え、`max_position_embeddings` を拡張する | 事前学習時の短いコンテキスト長（`seq_len=1024`）で計算効率を最大化し、長文適応は事後の低コストな Continued Pretraining で達成するため |
| 事前学習 config.yaml + HPO 成果物の自動継承 | `configs/config.yaml` と `last_run_result.json` を自動マージし、LR を `extension_lr_factor` で減衰させる | 事前学習のハイパーパラメータを手動で再入力する必要を排除し、破壊的な高 LR による重み崩壊を防止するため |

### 5.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| 事前学習時の長コンテキスト学習 | 事前学習フェーズでは短いコンテキスト長（`seq_len=1024`）を使用し、長文対応は事後拡張に委ねる | 長コンテキストは VRAM 消費が $O(n^2)$ で増加し、事前学習の計算効率を著しく低下させるため。短コンテキスト + 事後拡張の 2 段階アプローチの方が総計算コストが低い |

## 6. 設定管理アーキテクチャ

### 6.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| 3 層設定合成 (`config.yaml` = `base_config` + `scaling_config` + `hpo_config`) | Hydra の `defaults` リストにより、インフラ固定設定 / スケーリング法則成果物 / HPO 成果物を宣言的に合成する | 各成果物の生成タイミングが異なる（Scaling → HPO → Training の一方通行）ため、ファイル単位で責務を分離し、上書きの優先順位を明示する |
| 設定正規化 (`_normalize_config`) | ネスト構造の YAML を学習パイプライン用のフラットな dict に変換し、デフォルト値補完・学習率クリッピング・バッチ分割・`max_steps` 動的逆算を一括処理する | 設定の検証と変換を単一関数に集約し、呼び出し元ごとの重複ロジックを排除するため |
| 非 Linux 環境での Triton 自動無効化 | `sys.platform != "linux"` の場合、`torch_compile` と `use_liger_kernel` を自動的に `False` に設定する | Triton は Linux カーネルの CUDA ドライバを前提としており、Windows 環境では動作保証がないため |
| WSL パス自動解決 | Windows 形式の絶対パス（`C:\...`）を WSL 形式（`/mnt/c/...`）に再帰的に変換する | WSL2 環境で Windows 側のパスが設定ファイルに残存する場合のパス解決エラーを防止するため |

### 6.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| GUI / Web UI による設定管理 | 全設定を YAML + CLI のテキストインターフェースで管理する | GUI は設定の diff / merge / Git 管理が困難になり、再現性を損なうため |
| 設定ファイルのランタイム動的リロード | 学習開始時に設定を一括ロードし、学習中の設定変更は許容しない | 学習中の設定変更はハッシュ検証との矛盾を生み、トレーサビリティを破壊するため |

## 8. 環境互換性方針

### 8.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| WSL2 + Windows WDDM 環境の TDR 対策 | 起動時に Windows レジストリの `TdrDelay` / `TdrDdiDelay` を確認し、不足時にアクション案内を出力する | Triton JIT コンパイルが 10~30 秒かかる場合、Windows のデフォルト TDR タイムアウト（2 秒）で GPU ドライバリセットが発生するため |
| `/mnt/` ストレージアクセスの性能警告 | データセットパスが WSL の `/mnt/` 配下（Windows ファイルシステム経由）に解決された場合、パフォーマンス警告を出力する | WSL2 → Windows ファイルシステムのアクセスは 10~20 倍遅く、学習速度のボトルネックとなるため |
| トークナイズ並列化のプラットフォーム分岐 | Windows: `ThreadPoolExecutor`（pickle 問題回避）、Linux: `multiprocessing`（プロセス並列） | Windows の `multiprocessing` は Tokenizer オブジェクトの pickle に失敗するケースがあるため |
| `/tmp` (tmpfs) の容量不足回避 | `TMPDIR` をローカルディスク上のディレクトリに強制指定する | Linux の `/tmp` が tmpfs（RAMディスク）の場合、チェックポイント書き込み等で `[Errno 28] No space left on device` が発生するため |

### 8.2 実装しない

| 対象 | 方針 | 根拠 |
|------|------|------|
| macOS / Apple Silicon (MPS) の能動的サポート | CUDA を前提とし、MPS バックエンドの動作保証は行わない | MPS は PyTorch の CUDA API と互換性が不完全であり、Muon / Liger Kernel / FlashAttention 等の主要コンポーネントが動作しないため |

## 11. 学習率スケジューラ方針

### 11.1 実装する

| 対象 | 方針 | 根拠 |
|------|------|------|
| Constant + Cosine Decay スケジューラ | Warmup → Constant (定常期) → Cosine Decay の 3 フェーズ構成を Step Law / Muon 推奨設定として採用する | Muon の Newton-Schulz 直交化は学習初期の LR 安定性に敏感であり、Constant フェーズが初期の勾配ノルム安定化に寄与するため |
| `SplitOptimizer` 対応の単一 `LambdaLR` | Muon + AdamW の統合 `param_groups` に対して単一のスケジューラを適用し、`max_lr_2d : max_lr_1d` の比率を保持する | 複数スケジューラの管理は設定の複雑化と同期ミスのリスクを招くため |

## 12. 優先順位原則

### 12.1 開発・実験フェーズ（イテレーション速度優先）

```
精度 < コンテキスト長 < VRAMの使用効率 < モデルサイズ < 学習時間の短縮 < データ収集
```

**根拠**: 検証段階では「イテレーション回数と試行速度 (Time to Insight)」が最重要。VRAM 消費削減のためにオーバーヘッドを増加させるより、学習速度を優先してフィードバックサイクルを高速化する。

### 12.2 本番・大規模学習フェーズ（リソース限界到達時）

```
精度 < 学習時間の短縮 < コンテキスト長 < VRAMの使用効率 < モデルサイズ < データ収集
```

**根拠**: 本番フェーズでは計算予算の限界まで到達するため、VRAM の使用効率向上によるモデルサイズ拡大が学習時間短縮よりも優先される。

## 13. アーキテクチャ設計原則

| 原則 | 適用方法 | 根拠 |
|------|----------|------|
| 起動時ハードウェア診断 → 設定自動生成 | VRAM 検出 / TDR チェック / OS 判定 / CPU コア数 / ストレージ種別を起動時に一括診断し、最適設定を自動生成する | 人手による環境固有の設定チューニングを排除し、「コマンド一発で任意環境で実行可能」にするため |
| Single Source of Truth (SSOT) | 定数・安全上限・バッチ算定式を単一モジュール（`constants.py`, `vram_estimator.py`）に集約する | 同一ロジックの散在は設定値の不整合を招くため |
| Defense in Depth (多重防御) | 学習率クリッピング・VRAM 推定・発散検知・ハッシュ検証の各ガードを独立かつ重複して配置する | 単一の防御層が突破された場合でも後段のガードで安全性を確保するため |
| 一方通行 DAG (循環依存排除) | Scaling Laws → HPO → Training → Context Extension のデータフローに循環を一切持たせない | 循環依存は設定変更の影響範囲を不透明にし、デバッグを困難にするため |
| 汎用ロジック + 設定ファイルによるドメイン固有化 | ハードコードされた分岐 (`if 150M`, `elif 3B`) を排除し、数式・べき乗則で連続的にスケールするロジックを実装する | モデル規模や GPU 環境の変更時にソースコード修正を不要にするため |
